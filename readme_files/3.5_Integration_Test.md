# 3.5 Integration Test

## High-Level Overview

`zero2prod` is a Rust web application built incrementally following the *Zero To Production In Rust* book. At this stage, the project consists of a minimal HTTP server with a single `health_check` endpoint. The primary goal of this chapter is to verify that the application can be started and responds correctly to HTTP requests via an **integration test** that exercises the full stack — from the TCP listener through the HTTP router to the request handler.

Rather than testing functions in isolation (unit tests), the integration test launches the real application as a background task and issues actual HTTP requests against it using an HTTP client. This validates the wiring between the web framework, the server runtime, and the business logic.

## Technical Overview

### Project Structure

```
zero2prod/
├── Cargo.toml
├── src/
│   ├── lib.rs      # Application logic and server builder
│   └── main.rs     # Binary entrypoint
└── tests/
    └── health_check.rs  # Integration test suite
```

### Dual-Crate Layout (Library + Binary)

`Cargo.toml` declares both a library (`src/lib.rs`) and a binary (`src/main.rs`):

```toml
[lib]
path = "src/lib.rs"

[[bin]]
name = "zero2prod"
path = "src/main.rs"
```

This split is intentional:

- **`src/lib.rs`** contains the reusable application code. It defines routes, handlers, and a `run()` function that constructs and returns an `actix_web::dev::Server`.
- **`src/main.rs`** is the thin binary wrapper. It imports `run` from the library, calls it, and `.await`s the resulting `Server`.
- **`tests/health_check.rs`** is an external integration test crate that depends on the library. It can import `zero2prod::run` directly to launch the application for testing.

### The `run()` Function

`run()` was refactored from an `async fn` into a **synchronous function** that returns `Result<Server, std::io::Error>`:

```rust
use actix_web::{App, HttpResponse, HttpServer, web, dev::Server};

pub fn run() -> Result<Server, std::io::Error> {
    let server = HttpServer::new(|| {
        App::new()
            .route("/health_check", web::get().to(health_check))
    })
    .bind("127.0.0.1:8000")?
    .run();

    Ok(server)
}
```

Key design decisions:

- **No `.await` inside `run()`**: `HttpServer::bind(...).run()` returns a `Server` future, but it does not need to be awaited here. By returning the `Server` handle, the caller decides *when* and *where* to await it.
- **`Server` comes from `actix_web::dev::Server`**: This is the type returned by `HttpServer::run()`. It must be imported explicitly.
- **Caller-side `await`**: In `main.rs`, the binary calls `run()?.await` — the `?` bubbles up binding errors (e.g., port already in use), and `.await` starts the event loop.

### The `health_check` Handler

```rust
async fn health_check() -> HttpResponse {
    HttpResponse::Ok().finish()
}
```

This is the simplest possible Actix-web handler: it responds with `200 OK` and an empty body. The integration test asserts exactly this behavior.

### Integration Test (`tests/health_check.rs`)

```rust
#[tokio::test]
async fn health_check_works() {
    // Arrange
    spawn_app();

    let client = reqwest::Client::new();

    // Act
    let response = client
        .get("http://127.0.0.1:8000/health_check")
        .send()
        .await
        .expect("Failed to execute request.");

    // Assert
    assert!(response.status().is_success());
    assert_eq!(Some(0), response.content_length());
}
```

The test follows the **Arrange-Act-Assert** pattern:

1. **Arrange**: Call `spawn_app()` to launch the server in the background. Create an HTTP client via `reqwest`.
2. **Act**: Send a `GET` request to the local health check endpoint.
3. **Assert**: Verify the response status is successful (`2xx`) and the body is empty (`content_length() == 0`).

### Spawning the App in the Background

```rust
fn spawn_app() {
    let server = zero2prod::run().expect("Failed to bind address");
    let _ = tokio::spawn(server);
}
```

- `zero2prod::run()` constructs the `Server` handle. If binding to `127.0.0.1:8000` fails (e.g., port in use), it panics immediately.
- `tokio::spawn(server)` submits the server future to the Tokio runtime as a background task. The test continues executing concurrently while the server listens for connections.
- The `let _ =` discard is intentional: we do not need the `JoinHandle` because we never await the server's completion.

### Runtime Architecture

Both the application and the test use **Tokio**:

- `main.rs` uses `#[tokio::main]` to run the async `main()` function.
- The test uses `#[tokio::test]`, which spins up a single-threaded or multi-threaded Tokio runtime for the test.
- `tokio::spawn` works inside the test because `#[tokio::test]` provides a runtime context.

### Dependencies

| Crate | Role |
|-------|------|
| `actix-web` | Web framework: routing, HTTP server, request/response types |
| `tokio` | Async runtime: executor, `spawn`, `#[tokio::main]`, `#[tokio::test]` |
| `reqwest` | HTTP client for integration tests |

### Known Limitations at This Stage

- **Hard-coded port**: Both the app and the test assume `127.0.0.1:8000`. If the port is occupied, the app or test will fail.
- **Race condition**: `spawn_app` returns immediately after spawning the server task, but the OS socket may not be fully listening yet. In practice this is usually fine for local tests, but a more robust setup would wait for a "ready" signal.
- **No graceful shutdown**: There is no mechanism to stop the server when the test ends; it runs until the test process exits.

These issues are addressed later in the book by switching to **random OS-assigned ports** and introducing **application builders** with configuration structs.

## Summary

At this point in the project, the architecture is:

1. **Library** (`lib.rs`) exposes a `run()` function that builds an Actix-web `Server`.
2. **Binary** (`main.rs`) calls `run()` and awaits it to start serving traffic.
3. **Integration test** (`tests/health_check.rs`) imports the library, spawns the server in a background Tokio task, and verifies the `health_check` endpoint using `reqwest`.

This pattern — library for logic, binary for execution, integration tests against the real server — is the foundation for the more complex features (database connections, email dispatch, background jobs) that come later.
